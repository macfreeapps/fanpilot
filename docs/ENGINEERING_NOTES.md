# FanPilot engineering notes

A build-by-build log of what changed, what was measured on real hardware, and what was **not** verified. Newest first. Hardware results are from a single MacBook Pro (M4 Pro, `Mac16,8`) unless stated otherwise. For a short summary see [CHANGELOG.md](../CHANGELOG.md).

Build 20 adds an About tab as the last tab in Settings: app icon, version and build, "Made by @tarudesu", a one-line description, and three short notes (safe by design, maximum cooling at 95°C shown in your unit, MIT licence). The earlier About row on the Fan Control tab moved here.

Build 19 makes the modes easier to understand. Normal / Daily / Turbo (who controls the fans) and Quiet / Balanced / Cool (how Daily behaves) were two separate-looking choices in different places with no explanation of how they relate. Now: a one-sentence explanation of the selected mode sits under the mode cards ("Daily: FanPilot keeps your Mac cool but quiet. Fans rest until they're needed."); when Daily is selected, a small "How should Daily work?" card appears right under the cards with Quieter / Balanced / Cooler (named as a scale, with a plain description and the actual start temperature in your unit), and it disappears for Normal and Turbo; the same compact control is in the menu-bar panel; the Settings tab "Cooling" is renamed "Daily Mode", titled "How should Daily mode work?", and says these choices only apply in Daily mode. The default window is taller so the extra card fits without scrolling.

Builds 17 and 18 make the Menu Bar options in Settings behave exactly like the real menu-bar item. Checking the real menu bar against Settings found three mismatches: "Both" showed only the temperature (a SwiftUI menu-bar label renders a single text item, so the second value was silently dropped), "Fan speed" showed a bare number with no unit, and the mode colour shown in the Settings preview never appeared in the real menu bar (macOS draws menu-bar images monochrome). The menu-bar text now comes from one tested function (`MenuBarFormat`, 26 tests) that both the real item and the Settings preview use: Icon shows nothing extra, Temperature shows e.g. "74°C" or "165°F", Fan speed shows e.g. "2520 rpm", Both shows "69°C  ·  2494 rpm". The icon is a plain template icon in Normal and a coloured icon (blue Daily, orange Turbo, filled fan in Turbo) when FanPilot is controlling the fans, and the preview draws the identical image. Also fixed: after the helper restarts it can keep reporting "another fan utility may be controlling this Mac" until the next request re-checks, even though nothing is wrong; that stale warning is no longer shown unless a fan is actually under manual control. Verified by capturing the real menu bar for each option.

Build 16 fixes the Settings button in the menu-bar panel doing nothing. `SettingsLink` does not activate the app from a menu-bar panel and does not bring an already-open Settings window forward, so it now uses a button that activates FanPilot, opens Settings, and raises the Settings window if it already exists (the same button is used in the main window). Verified through the accessibility route: it opens Settings, and pressing it again leaves a single Settings window. The click from the menu-bar panel itself was not driven on screen.

Build 15 adds a "Made by @tarudesu" credit to the About row in Settings > Fan Control and to the standard About FanPilot panel (app menu).

Build 14 redesigns Settings and adds two options (app changes only; the helper's behaviour is unchanged, but its binary differs from build 13's because it links the shared FanCore library that gained the temperature-unit type, so Settings > Fan Control > Update Helper will offer a harmless, optional refresh; the build 13 helper keeps working). Settings is now four tabs in the standard macOS toolbar style, built from the same cards as the main window, each row with an icon and a plain-language explanation: **General** (temperature unit, open at login, remember last mode), **Menu Bar**, **Cooling** (Quiet / Balanced / Cool style cards, with the expert controls behind "Fine-tune") and **Fan Control** (helper status, turn on / update / remove, save a report, version). **Show or hide FanPilot in the menu bar:** a switch on the Menu Bar tab; when it is on, a live preview of the menu-bar text sits above a Icon / Temperature / Fan speed / Both choice. Hiding the menu-bar item does not stop FanPilot or change the fans, and the app stays in the Dock. **Temperature unit:** Celsius or Fahrenheit, defaulting to Fahrenheit in the US and Celsius elsewhere, applied everywhere a temperature is shown (main readout, sensor list, menu bar, Fine-tune sliders; a Fine-tune "difference" such as 8 °C is shown as 14 °F, not 46 °F). Control logic and stored settings stay in Celsius. The unit conversions live in the tested core library (25 tests). Verified on the M4 Pro: switching the unit updated the main window, menu bar and Settings immediately; the menu-bar switch removed and restored the item with the app still running.

Build 13 is a full redesign of the interface for non-technical users (app only; the helper is unchanged). One calm window: an animated fan inside a temperature gauge, a plain-language headline ("Cool and quiet", "Keeping your Mac cool", "Maximum cooling"), three mode cards (Normal, Daily, Turbo, each with a one-line description), a friendly fan list ("Resting", "75%") and a collapsed Details section for sensors and RPM. The fan spins at a speed that follows the real fan speed, winds down when it stops, and changes colour with the mode; the gauge colour follows the temperature; the mode selection slides between cards, the number and headline cross-fade, and banners slide in. A brand-new user sees a single "Turn On Fan Control" card instead of hunting through Settings, and a short animated welcome screen. Settings is simplified: a Quiet / Balanced / Cool style for Daily mode with the expert sliders behind "Fine-tune", plain-language fan-control status and a "Save Report" button. Error messages are rewritten in plain language. The menu-bar panel is a compact version of the same view. Reduce Motion is respected (the fan stays still), controls have VoiceOver labels (the mode cards, details toggle, and every Settings control are labeled), and the interface follows light and dark appearance; it was checked in both on the M4 Pro, which found pale temperature text unreadable on white, so temperature text now uses a darker shade in light mode. VoiceOver itself was not run (the accessibility tree and labels were audited instead). Performance work that came out of measuring it: the displayed temperature is the median of the last few seconds (the raw hottest-sensor reading jumps by 10-20°C every second), displayed fan speeds are rounded to 5% steps, and the fan rotation runs in Core Animation from a cached bitmap, because SwiftUI animations on macOS render on the CPU and steady fans must produce a steady screen. Measured on the M4 Pro: about 0.5% CPU in Normal with the window open, about 3.5% in Turbo with both fans spinning (5-minute average), about 0.5-1.6% with the window closed.

Builds 11 and 12 are a fan-safety code review with fixes (helper and app; **the helper must be updated through Settings > Install / Update**). Findings and changes: (1) **Sensor discovery froze the control sensor set at helper startup.** Sensors that read invalid at that instant (for example idle P-core clusters that are powered off) were dropped permanently, so after a quiet start Daily and the 95°C emergency check could be blind to the hottest sensors under load. Discovery now keeps every temperature key by type and validity is applied to each sample (unit-tested). (2) **A failed startup recovery silently disabled the safety machinery**: timers, signal handlers and the heartbeat watchdog were never started and nothing retried. They now always start, a failed recovery is retried every 5 s, a corrupt or unreadable state file counts as "needs recovery", and an unrecognized fan state refuses control instead of throwing away the setup. (3) **New last-resort path**: when control cannot be maintained (sensor failure, lost heartbeat, closed connection, failed mode change) the helper restores system control and, if even that fails, drives the fans to maximum rather than leaving a stale, possibly low, manual target. A failed mode change now rolls back any partial engagement (one fan manual, one automatic). (4) **Independent liveness watchdog** on its own queue: if a manual mode is active and the control loop has not run for 40 s (for example a hung SMC call), it tries to release the fans and exits so launchd restarts the helper and startup recovery runs. (5) **macOS thermal pressure** `serious` (not only `critical`) now forces maximum cooling, which also covers heat the CPU/GPU die sensors do not capture. (6) The XPC client check now uses `setCodeSigningRequirement` (enforced against the audit token) instead of a PID lookup, which could be raced by PID reuse. (7) The heartbeat age is reset on wake so a sleep is never mistaken for a dead app. (8) The helper's snapshot returned discovery-time sensor values, so the menu panel could show a frozen temperature; the panel now reads the app's own live sensors. (9) Build 10's "show the helper's real mode" sync had introduced a feedback loop (a helper-side change re-sent a mode request, which the helper then refused as another tool); only user actions send mode requests now, and the helper treats a repeat of the active mode with unchanged settings as a no-op. Verified on the M4 Pro with the new helper: Turbo from cold reaches both maximums in about 8 s; `kill -9` of the helper in Turbo returned both fans to system control about 1 s later with the window correctly showing Normal; the app connects through the new code-signing requirement.

Build 10 changes one thing in the app: the mode shown in the window now follows the mode the helper actually reports (when no change is in flight). Before, after a helper restart or a refused request the window kept showing the mode you had selected (for example "Turbo" with the fans at 0 RPM). It is app-only; the helper binary is unchanged from build 8.

Build 10 hardware verification on a MacBook Pro M4 Pro (Mac16,8), continuing build 9's results. **Sleep/wake:** with Turbo active, a real 2-minute system sleep (verified by a gap in the recorder timestamps) reset the SMC to automatic mode 3 / 0 RPM on wake; the helper re-engaged Turbo by itself about 7 s after wake and both fans were back near 7,800 RPM by about 9 s (the plan's target is 5 s; the helper waits 2 s after wake and the M4 unlock takes 3-5 s). The 15 s heartbeat watchdog did not drop control across the sleep. **Competing fan tool:** `fanpilotctl test-engage` (run as root) held fan 0 manually with `Ftst=1`; choosing Daily in FanPilot was refused with the "Another fan utility may be controlling this Mac" warning and wrote nothing (the other fan stayed at system level); after that tool released, choosing Daily was accepted without restarting the helper. This used a stand-in tool; Macs Fan Control itself is not installed here. **Helper `kill -9`:** killing the root helper process while Turbo was active (PID 40912 to 84354, launchd `runs = 2`) left both fans back under system control (mode 3, `Ftst=0`) via the persisted-state recovery, with no manual intervention. **Clean uninstall/install:** Settings > Uninstall while Turbo was active restored system control first, then removed the helper binary, LaunchDaemon plist, launchd job and state directory; a fresh copy from the DMG with preferences wiped showed the onboarding sheet and monitor-only controls, reported the helper as Not installed, installed it from scratch (root:wheel, byte-identical to the bundled helper), connected, and Turbo/Normal worked. This was a same-user cycle, not a separate macOS user account.

Observations: single-sample spikes in the per-core die sensors (about 75-80°C for one second at idle) repeatedly re-trigger Daily's fast heating response, so on this Mac Daily tends to stay engaged at roughly 2,300-5,000 RPM at idle instead of handing the fans back; a median-of-three filter on the control temperature would be the likely fix. The helper uses about 1-3% CPU while a mode is active because it reads every sensor each second.

Build 9 fixes three bugs found while verifying build 8 on hardware. (1) The menu-bar **Quit** button deadlocked the app: it restored fan control and then called `terminate`, whose own restore reply needed the main actor that the first handler still held, so the app froze. Quit now only calls `terminate`, and `applicationShouldTerminate` replies after at most 5 s even if the helper is slow. (2) **Install / Update** did nothing on Apple Development builds: `SMAppService` accepted the registration (or failed outside the error handling) and the administrator-prompt install never ran. Builds that are not Developer ID signed now go straight to the administrator-prompt install. (3) **Remember last mode** did not reapply at launch; the selected mode and the once-per-launch reapply now live in `HelperClient`. Installer error messages in Settings also wrap instead of being cut off.

Build 9 hardware verification on a MacBook Pro M4 Pro (Mac16,8) with the build 8/9 helper (helper updated via the in-app administrator prompt): Turbo took both fans to the 7,826 RPM maximum within 3 s; Quit from Turbo exited cleanly and returned both fans to system control with `Ftst=0`; `kill -9` of the app in Turbo returned the fans to system control in about 1 s; relaunching reapplied the remembered mode; Turbo to Daily stepped the fans down at about 165 RPM/s (the 3% ramp-down) without a sudden drop. **The 20-minute sustained-load test passed**: 12 CPU burners for 1,195 s in Daily, hottest CPU/GPU die sensor max 87.8°C (mean 80.7°C, never 95°C or above), fans stayed manual with an average of about 7,700 RPM, and `kernel_task` averaged 15.9% (max 20.1%) against a 13–15% idle baseline, so no thermal-throttling signature. Observation: on this Mac the hottest die sensor idles around 62°C even under system control, where macOS itself runs the fans at their 2,317 RPM minimum, so the 60°C default start is equivalent to macOS behavior there; Daily just does not release until the sensor stays 8°C below start. Still unverified: sleep/wake, a live Macs Fan Control conflict, the helper `kill -9` recovery with the build 8 persistence change (needs root), a clean install on a fresh user, and the 8-hour soak.

Build 8 fixes a helper safety gap: after Daily released the fans and later re-engaged on its own, the persisted intent file still said "not dirty", so a helper crash at that moment would have been treated as another tool's manual control and not recovered. The helper now persists intent before every manual engage. It also re-checks a latched "another fan utility" conflict when a mode is requested (so quitting Macs Fan Control no longer requires a helper restart), answers `snapshot` asynchronously so the 3–6 s M3/M4 unlock never ties up XPC threads, and the UI shows "Unlocking fan control…" while a mode change is in flight. The menu-bar label refreshes at most every 3 s unless temperature moves 3°C or more. `fanpilotctl` gained `test-engage` and `restore`, two Daily trace tests were added (23 total), and the CI workflow was fixed (`maxim-lobanov/setup-xcode`, XcodeGen installed). **The helper change only takes effect after Settings → Install / Update** (administrator prompt); until then the previous build 7 helper keeps running and remains compatible with the app. Idle CPU with the main window open measured roughly 2–5% on the M4 Pro (mostly SMC polling and status-item redraws); the earlier 0.3% figure was with the window closed.

Build 6 added hottest-sensor refresh to adaptive sensor polling, first-launch onboarding, and the XPC reconnect fix. Build 7 decouples the menu bar label from full sensor updates and caches static fan limits to reduce idle CPU use while retaining one-second readings. On a MacBook Pro M4 Pro (Mac16,8), Turbo reached both maximum targets and brought fan tach readings within 50 RPM of maximum; Normal restored firmware automatic mode `3`, target `0`, and `Ftst=0`. Daily engaged both fans near 4,889 RPM at about 75°C, then Normal restored automatic control. Force-killing the app while Turbo was active restored automatic control. Killing the helper in Turbo caused launchd to restart it and startup recovery returned the fans to system control. The app is installed at `/Applications/FanPilot.app` and packaged as an arm64 DMG.

The app is signed with the local Apple Development identity and is not notarized. All 21 `FanCore` tests pass. Before build 7, a short idle sample measured about 2.1% CPU. After the build 7 polling and menu updates, a 25-second idle sample with the main window closed averaged 0.3% CPU (`ps` reported 0.1% after 93 seconds), meeting the plan's below-1% target in this run. A CPU/GPU load check was stopped before 20 minutes after the hottest reported sensor reached 107°C. Daily entered emergency cooling and drove both fans to maximum; after stopping the load, the readings fell and Normal restored firmware fan control. This validates the emergency response observed in that run, but does not pass the planned 20-minute sustained-load test; `kernel_task` behavior in a completed run remains unverified. Sleep/wake, live Macs Fan Control conflict, clean install/uninstall on a fresh user, and the 8-hour soak also remain unverified.

The v1.0 DMG is a local arm64 release. `hdiutil verify` succeeds, and the installed app launches with firmware fan control active. Gatekeeper rejects this non-notarized development build on this Mac; users may need to approve or remove quarantine manually. Public distribution needs Developer ID signing and notarization.

## Builds 1-7: initial release

Initial macOS release.

- Menu-bar status for hottest CPU/GPU temperature and live fan speeds.
- Normal, Daily, and Turbo modes with a root LaunchDaemon for fan control.
- SMC key and sensor discovery at runtime, with M4-specific mode-key and `Ftst` path confirmed by the saved read-only diagnostic.
- M4 automatic handoff accepts firmware's automatic mode value `3`, and manual engagement retries until the SMC acknowledges mode `1`.
- Main-window control status and helper errors are shown separately from the selected mode.
- Daily cooling curve, hysteresis, asymmetric temperature filtering, clamped RPM targets, maximum-speed emergency handling, and system-control restoration.
- Helper heartbeat, persistent dirty state, startup recovery, signal handling, and sleep/wake reassertion.
- Automatic XPC reconnection after helper restart; remembered mode is reapplied once per app launch so a helper recovery stays in Normal.
- Diagnostics export and a 1024-pixel macOS-style app icon.
- First-launch onboarding explains the privileged helper and detects fanless Macs for monitoring-only guidance.
- Fan RPM and the hottest five CPU/GPU sensor readings refresh every second; the full sensor set refreshes every five seconds to reduce SMC traffic.
- The menu bar observes only its displayed rounded temperature and RPM values, avoiding status-item redraws on unchanged sensor updates.
- Fan minimum and maximum RPM bounds are read once and reused for monitoring snapshots.
